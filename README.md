# PulseOps

PulseOps is a web service monitoring application under development.
Its goal is to track availability, response times, and health check history.

## Current status

A first FastAPI endpoint is available: `GET /health` returns `{"status":"ok"}`.
It confirms that the API responds; it does not check a database or other services.
PostgreSQL runs locally through Docker Compose with a named data volume.
The Python database connection is configured in `backend/database.py`.
The Service model describes names, URLs, positive check intervals in seconds,
and creation timestamps. The schema is managed with Alembic migrations.
The API exposes CRUD endpoints for services (see below). The dashboard is not implemented.

## Planned stack

- Backend: Python, FastAPI, SQLAlchemy, PostgreSQL
- Frontend: React, TypeScript, Vite, Tailwind CSS
- Infrastructure: Docker Compose, GitHub Actions
- Observability after the MVP: Prometheus and Grafana

## Local development

The backend currently uses Python 3.14. Run these commands from the repository root:

```bash
python3 -m venv backend/.venv
source backend/.venv/bin/activate
python -m pip install -r backend/requirements.txt
fastapi dev backend/main.py
```

On Ubuntu, if environment creation fails because `ensurepip` is missing,
install the venv package matching your Python version (for example,
`sudo apt install python3.14-venv`) and retry.

In a second terminal:

```bash
curl -i http://127.0.0.1:8000/health
```

Expected response: HTTP `200 OK` with the JSON body `{"status":"ok"}`.
Interactive API documentation is available at <http://127.0.0.1:8000/docs>.
Stop the server with `Ctrl+C`.

The virtual environment is created once. Activate it again in each new terminal
used to run the backend. Dependencies are pinned in `backend/requirements.txt`
from the current Linux development environment.

## Local database

Docker and Docker Compose are required. From the repository root, copy the
example only if you do not already have a `.env` file:

```bash
cp .env.example .env
```

Set `POSTGRES_PASSWORD` in `.env` to a local password, then start the database:

```bash
docker compose up -d --wait postgres
docker compose ps
```

The database is `pulseops`, with user `pulseops`, at `127.0.0.1:5433` by default.
Set `POSTGRES_PORT` in `.env` to choose another host port. PostgreSQL still listens
on port `5432` inside its container. The published port is limited to localhost.

To open a SQL session with the configured user and database:

```bash
docker compose exec postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```

Try `SELECT current_database(), current_user;` and use `\q` to exit.
This checks PostgreSQL directly. Python uses SQLAlchemy with the Psycopg driver;
`backend/database.py` reads the root `.env` and configures a connection to
`127.0.0.1:5433` by default. Existing environment variables take precedence.
`POSTGRES_HOST` can override the host when needed.

With PostgreSQL running and the virtual environment activated, apply the
database migrations from the repository root:

```bash
alembic upgrade head
```

Migrations live in `backend/migrations/versions/`. Alembic records the applied
revision in the `alembic_version` table. After changing a model, generate a
migration with `alembic revision --autogenerate -m "<message>"`, review it, then
run `alembic upgrade head`. `alembic current` shows the applied revision.

If your database was created earlier with the removed `init_db` script, the
`services` table already exists: run `alembic stamp 940665df5b17` once to mark
it as migrated, then `alembic upgrade head`.
The `services` table contains `id`, `name`, `url`, `check_interval` (positive
seconds), and `created_at` (a timezone-aware timestamp generated by PostgreSQL).
URL validation will be added at the API layer with the service creation endpoint.

In `psql`, inspect the table with `\d services` or run
`SELECT id, name, url, check_interval, created_at FROM services;`.

Useful commands:

```bash
docker compose logs --tail=50 postgres
docker compose stop postgres
docker compose start postgres
```

The named volume `postgres_data` is mounted at `/var/lib/postgresql/data`, the
data directory used by this PostgreSQL 17 image. `docker compose down` preserves
the volume; `docker compose down -v` deletes it and its database data.

The `POSTGRES_*` initialization variables only create the database and user when
the data directory is empty. Editing `.env` later does not change an existing
database password. This setup is for local development.

## Services API

| Method | Path | Success | Errors |
|---|---|---|---|
| `POST` | `/services` | `201` created service | `422` invalid body |
| `GET` | `/services` | `200` list | |
| `GET` | `/services/{service_id}` | `200` service | `404`, `422` |
| `DELETE` | `/services/{service_id}` | `204` | `404`, `422` |

Request body for creation: `{"name": "...", "url": "https://...", "check_interval": 60}`.

## Development workflow

Keep `main` working and use a short-lived branch for each focused change:

- `chore/project-setup`
- `feat/health-endpoint`
- `feat/postgres-setup`
- `fix/<short-description>`

Open a pull request against `main`, describe the change and how it was checked,
review the diff, then squash and merge. Delete the merged branch and start the
next branch from an updated `main`.

Use descriptive commit messages, for example:

```text
chore(repo): initialize project structure
feat(api): add health endpoint
```

Commit environment variable examples with dummy values in `.env.example`.
Keep real credentials, `.env` files, virtual environments, and generated
dependencies out of Git.
